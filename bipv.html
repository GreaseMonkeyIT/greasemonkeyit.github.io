Problem Statement

SIH1739 — posed by ISRO / VEDAS

India's VEDAS portal (Visualisation of Earth Observation Data and Archival System) hosts 3D city models derived from Cartosat-2/3 satellite data. These LOD-1 models extrude building footprints to uniform heights, capturing the urban form of any Indian city. The problem: no open-source tool existed to use these models for citywide Building Integrated Photovoltaic (BIPV) potential estimation at scale.

Popular commercial CAD tools for Architecture and Civil Engineering uses like Ladybug/Rhinoceros work well only at single-building or neighbourhood levels, losing stability and scaling for city-scale use cases. ESRI CityEngine and Cesium; popular tools for creating 3D globes and 2D maps in a web browser, can handle visualisation, but not irradiance simulation. No public-domain software addressed citywide BIPV estimation.

The desired outcome therefore was: given a date and irradiance parameters, generate a 3D city model rendered per-face by solar energy potential, identifying optimal BIPV zones for architects, urban planners, and policymakers.

Data Inputs

Open data, no proprietary dependencies

Geometry
Cartosat + OpenStreetMap
Building footprints from ISRO's Cartosat shapefiles, cross-verified with Google Satellite imagery. Cleaned in QGIS: intersecting polygons removed, irrelevant faces stripped. Output is a clean multi-polygon shapefile ready for the 3D engine.
Irradiance Data
EnergyPlus Weather (EPW)
EPW files encode all 8760 hours of a year for a city: Direct Normal Irradiance, Diffuse Horizontal Irradiance, Global Horizontal Irradiance, plus sun azimuth and zenith for every hour. This replaces the original spec's single daily GHI input with a full annual model.
Elevation
DEM / DSM
Digital Elevation and Surface Models used to derive building heights for LOD-1 extrusion. Where Cartosat height attributes are available, those take precedence. Terrain elevation normalises the building base correctly in sloped areas.
EPW sun path dome — Ahmedabad International AP. Annual solar radiation distribution: high irradiance band tracks the equatorial sun arc. Input to all 8760-hour irradiance calculations.
Core Engine

Custom BVH ray tracer in Unity compute shader

The central challenge was computing per-face irradiance across thousands of buildings simultaneously. A naive ray tracer that checks every ray against every building face is O(n²) — infeasible at city scale. The solution was a Bounding Volume Hierarchy (BVH) built over all building meshes, reducing each shadow query from O(n) to O(log n).

The ray tracer runs as a Unity compute shader (C#/HLSL), sampling points at 1 m² resolution per face. For each sample point and each hour in the EPW dataset, it casts a ray toward the sun position and tests against the BVH to determine shadow fraction. This approach handles a full city district in reasonable compute time without specialised ray tracing hardware.

BVH acceleration structure over city mesh — Unity editor. Each level subdivides bounding boxes recursively, reducing ray-building intersection tests from O(n) to O(log n).
Unity irradiance render output. Rooftops and south-facing facades show highest values (red/orange); shadowed north faces and occluded walls show lower values (blue/green).
Irradiance Formula
Total irradiance per rooftop pixel R (summed over hemisphere patches)
R = Σi=0p [ (IωS + DS + G(1−S)α) ]
I = direct incidence radiation from patch i
D = diffuse radiation from patch i
G = global radiation from patch i
S = shadow value per patch (ray test result)
α = surface albedo (fraction of light reflected)
p = number of patches on the hemisphere

Sun incidence angle ω (accounts for face slope and sun position)
ω = sin(DSMslope) × cos(Sunaltitude) × cos(Sunazimuth − DSMaspect)
     + cos(DSMslope) × sin(Sunaltitude)

// For LOD-1 vertical faces: DSM_slope = 90°, simplifies to cos(Sun_altitude) × cos(Sun_azimuth − face_aspect)
// For rooftops: DSM_slope = 0°, simplifies to sin(Sun_altitude)
Unity compute shader (C#) — actual implementation. EPW hourly DNI/DHI/GHI lookup, BVH shadow fraction, outward face normal dot product, direct + diffuse + reflected accumulation per face per hour.
Visualisation

GeoJSON attribute map on Cesium.js

Once the Unity compute pass finishes, each building face's irradiance value is embedded as a feature attribute in a GeoJSON export — one polygon per wall segment or rooftop tile, carrying its annual irradiance in Wh/m². The UV map acts as the intermediate: face IDs in the mesh map to GeoJSON feature IDs, so every polygon knows exactly which baked value to carry. Cesium.js loads the GeoJSON, maps the irradiance attribute to a solar colour scale, and drapes the coloured polygons over satellite imagery as a 3D cityscape.

No irradiance computation happens in the browser — the viewer reads pre-baked values and renders them. At city zoom level the district-level gradient is visible; zoom into any block and the 1 m² tile resolution reveals fine-grained shadow patterns where adjacent buildings cast partial occlusion across neighbouring faces.

Per-face irradiance at building level. Rooftop faces render red (high annual irradiance, unobstructed). East/west facades show intermediate values. North-facing and occluded faces render blue-purple.
Design Decisions

Why these choices

Unity over CAD / GIS tools
Game engines are built to render and process large numbers of meshes simultaneously. Ladybug/Rhinoceros degrades badly past a few hundred buildings. Unity's ECS and compute shader pipeline handles an entire city district without per-frame CPU bottlenecks. The BVH is built once; shadow fractions and irradiance are computed entirely on the GPU via compute shaders, then baked into a UV map and exported as GeoJSON attributes. The browser viewer reads pre-baked values — irradiance computation never runs at view time.
EPW over single GHI input
The original problem spec asked for a single daily GHI value as input. EPW files are freely available for every major Indian city via EnergyPlus/Climate.OneBuilding and contain 8760 hours of hourly data including DNI, DHI, GHI, and pre-computed sun angles. Using EPW required no extra user input and gave annual irradiance maps instead of single-day snapshots — strictly more useful.
LOD-1 is sufficient for urban-scale assessment
LOD-1 extrudes footprints to flat-top boxes. Complex roof geometries (pitched, domed, stepped) are not captured. This is a known limitation; but for policy-scale decisions (which districts, which building clusters) the flat-top model introduces acceptable error. The paper validates this: results correctly identify high-potential zones even without LOD-2 geometry.
1 m² tile resolution
Finer resolution increases compute time quadratically. 1 m² was chosen as the crossover point where individual shadow edges are resolved but full-district computation remains tractable on consumer hardware. At this resolution, the irradiance gradient from a 10 m building casting shadow across an adjacent facade is clearly visible on zoom-in.

KiranShakti demonstrates that a citywide BIPV assessment tool can be built entirely on open data and open-source software. Cartosat geometry, EPW weather files, and QGIS are all freely available; the Unity compute shader and Cesium frontend are the novel contributions. The system identifies which buildings and which faces are optimal for BIPV installation at policy-relevant scale — the input level needed by architects, urban planners, and state energy departments.

Code is hosted on ISRO GitLab (private, per hackathon terms). The conference paper is published in the proceedings of the 40th Indian Engineering Congress, December 2025, Durgapur (paper ref: 285_EN 2025).
