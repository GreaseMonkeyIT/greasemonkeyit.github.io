What ASTA Does

Hospital ward monitoring without replacing hardware

ASTA mounts a camera on the bedside monitor, not the patient, and reads the display. Computer vision extracts structured vitals — heart rate, SpO₂, blood pressure, respiratory rate — from any OEM monitor brand with no API, no hardware tap, and no hospital IT integration required. A physiological reasoning layer detects deterioration and routes role-aware alerts to the right clinician.

The Vision Panel is the edge unit that sits at every bed. It runs the capture pipeline, transmits to the ASTA backend, and is managed entirely headless over SSH and Pi Connect. I designed and built the full embedded software stack — BSP, kernel config, camera pipeline, and power management — from bring-up in late 2024 through to hospital deployment.

Hardware

Platform overview

SoC
Raspberry Pi Zero 2W
ARM Cortex-A53 quad-core, 512MB RAM. Chosen for cost, form factor, and NEON FPU — essential for NEON-optimised OpenCV4 at the edge.
Camera
Camera Module 3 — IMX708
Sony IMX708 sensor via CSI-2. Driven by libcamera + rpicam-apps. Chosen for autofocus and low-light headroom needed in varied ward lighting conditions.
Cooling
Active 5V Fan
Forced-air cooling on the A53 cluster. The Zero 2W sustains thermal throttling under continuous OpenCV workloads without it — not optional for 24/7 operation.
Management
Headless — SSH + Pi Connect
No display, no keyboard. All configuration and updates over SSH. Pi Connect used for remote access when not on local network. Deployment requires zero physical interaction post-install.
Enclosure
3D-Printed
Custom PLA enclosure with camera aperture, fan mount, ventilation slots, and corner screw bosses for wall/monitor mounting. Iterated across two hardware revisions.

Buildroot BSP — selected config

The rootfs is built from scratch using Buildroot. GStreamer and FFmpeg were explicitly dropped — the pipeline does not need them and they would bloat the image past the 256MB target. Three sections from the config worth showing:

BSP / Kernel — bcm2709 defconfig, RPi linux fork, pinned commit
BR2_LINUX_KERNEL_CUSTOM_TARBALL=y
BR2_LINUX_KERNEL_DEFCONFIG="bcm2709"
BR2_LINUX_KERNEL_INTREE_DTS_NAME="broadcom/bcm2710-rpi-zero-2-w"
# Kernel commit pinned — not a floating tag. Reproducible builds across units.
Camera pipeline — libcamera IPA + rpicam-apps + OpenCV4 NEON
BR2_PACKAGE_LIBCAMERA=y
BR2_PACKAGE_LIBCAMERA_IPA=y  # imx708 in-process algorithm
BR2_PACKAGE_RPICAM_APPS=y   # rpicam-still, rpicam-vid, rpicam-raw
BR2_PACKAGE_OPENCV4_NEON=y   # NEON SIMD — required on A53 for usable throughput
BR2_PACKAGE_OPENCV4_PYTHON3=y
BR2_PACKAGE_OPENCV4_WITH_V4L=y
Rootfs target — 256MB, GStreamer and FFmpeg explicitly removed
BR2_TARGET_ROOTFS_EXT2_SIZE="256M"
# GStreamer and FFmpeg dropped — not used by this pipeline.
# libcamera + rpicam-apps + OpenCV4 + Python3 fits comfortably in 256M.
Engineering Decisions

Why these choices

Buildroot over Raspberry Pi OS
Pi OS ships a desktop, a browser, Bluetooth stack, audio servers, and a package manager — none of which exist in a headless ward unit. Buildroot gives a minimal, auditable rootfs with only what the pipeline needs. Boot time is faster, attack surface is smaller, and the image is reproducible across every unit from the same config.
libcamera + rpicam-apps over direct V4L2
The IMX708 requires in-process algorithm (IPA) support for autofocus and AEC/AGC. libcamera handles this correctly; raw V4L2 capture bypasses IPA and produces unusable frames in variable ward lighting. rpicam-apps sits on top of libcamera and gives reliable CLI capture — V4L2 videoio is forward-provisioned in the config for a future direct-capture path.
NEON-optimised OpenCV4 — not optional
The A53 without NEON runs OpenCV at roughly 3-4x lower throughput. Enabling BR2_PACKAGE_OPENCV4_NEON=y compiles with -mfpu=neon-vfpv4 and unlocks SIMD paths in imgproc and imgcodecs. For a continuous capture-and-process loop, this is the difference between keeping up with the frame rate and falling behind.
Active cooling — not a nice-to-have
The Zero 2W throttles the A53 cluster at sustained load above ~60°C. In a closed 3D-printed enclosure running a continuous CV workload, passive cooling does not hold the thermal budget. The 5V fan keeps the SoC in the sustained performance range across a full ward shift.
Pinned kernel commit, not a floating tag
Every unit in the field runs the same exact kernel. A floating tag (e.g. rpi-6.6.y) would drift between builds, making it impossible to reproduce a specific unit's environment for debugging. Pinning to a commit hash means the build is deterministic regardless of when it runs.
